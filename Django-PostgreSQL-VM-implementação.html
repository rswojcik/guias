Guia de execução para construir o sistema em Django + PostgreSQL, da VM zerada até o Admin em produção com MFA, versionamento de rotinas e aprovação multi-etapa.

Fase 0

Preparar a VM e o ambiente

Deixar o servidor e a máquina de desenvolvimento prontos, com um repositório Git próprio (self-hosted, sem depender de serviço externo) já ligando os dois.

0/6

Atualizar o sistema e instalar dependências de SO

No servidor

Pacotes de compilação e o próprio PostgreSQL precisam estar na VM antes do Python conseguir instalar tudo.

sudo apt update && sudo apt upgrade -y
sudo apt install -y python3-pip python3-venv python3-dev \
    build-essential libpq-dev postgresql postgresql-contrib git

Criar o banco e o usuário PostgreSQL

No servidor

Um banco dedicado, com um usuário próprio de aplicação — nunca rodar a aplicação como o superusuário do Postgres.

sudo -u postgres psql
CREATE DATABASE rotinas_secretarias;
CREATE USER rotinas_app WITH PASSWORD 'defina_uma_senha_forte';
ALTER ROLE rotinas_app SET client_encoding TO 'utf8';
GRANT ALL PRIVILEGES ON DATABASE rotinas_secretarias TO rotinas_app;
\q

Criar o usuário de deploy e o repositório Git bare

No servidor

Um usuário dedicado só para receber pushes (separado do usuário que roda a aplicação) deixa mais claro nos logs quem fez o quê. O repositório fica local, dentro da própria intranet — sem depender de GitHub/GitLab externo.

sudo adduser --disabled-password --gecos "" deploy
sudo -u deploy mkdir -p /home/deploy/rotinas-secretarias.git
sudo -u deploy git init --bare /home/deploy/rotinas-secretarias.git

Configurar acesso SSH sem senha da máquina de dev para o servidor

Na máquina de dev

Necessário para que o git push (e, mais adiante, o script de deploy automático) funcione sem pedir senha a cada vez.

ssh-keygen -t ed25519 -C "dev-rotinas"
ssh-copy-id deploy@servidor

Criar o ambiente virtual Python local

Na máquina de dev

Isola as dependências do projeto do Python do sistema. A mesma pasta será inicializada como repositório Git no próximo passo.

mkdir -p ~/apps/rotinas-secretarias && cd ~/apps/rotinas-secretarias
python3 -m venv .venv
source .venv/bin/activate

Inicializar o repositório local, apontar para o servidor e abrir no VS Code

Na máquina de dev

O repositório bare no servidor começa vazio — o primeiro git push só vai acontecer ao final da Fase 1, depois que o projeto Django existir. A partir daqui, o trabalho de código passa a ser feito com o Claude Code dentro desta pasta, como já definido no contexto do projeto.

git init
git remote add producao deploy@servidor:/home/deploy/rotinas-secretarias.git

Fase 2

Implementar os models

Traduzir o modelo de dados já fechado (Usuario, Secretaria, AcessoSecretaria, Rotina, VersaoRotina, EtapaAprovacao) em código, na ordem que respeita as dependências entre eles.

0/5

App contas: Usuario

Estende AbstractUser. É o primeiro model a existir, porque todos os outros dependem dele via settings.AUTH_USER_MODEL.

App secretarias: Secretaria e AcessoSecretaria

Inclui o campo aprovadora_global definido na etapa de regras de negócio.

App rotinas: Rotina, VersaoRotina, EtapaAprovacao

Nessa ordem — Rotina primeiro, depois VersaoRotina (que referencia Rotina), depois EtapaAprovacao (que referencia VersaoRotina). Adicionar history = HistoricalRecords() em Usuario, Secretaria, AcessoSecretaria, VersaoRotina e EtapaAprovacao, como definido anteriormente.

Referência-cruzada circularO FK versao_atual em Rotina aponta para VersaoRotina, que por sua vez tem FK para Rotina. Use string de referência ("rotinas.VersaoRotina") e crie o campo como null=True para não travar a primeira migração.

Gerar e revisar as migrações

python manage.py makemigrations contas secretarias rotinas
python manage.py sqlmigrate rotinas 0001   # ler antes de aplicar

Revisar o SQL gerado é especialmente importante aqui pelas normas ISO: qualquer alteração de schema em produção deveria estar documentada e revisável.

Aplicar migrações e criar o superusuário inicial

python manage.py migrate
python manage.py createsuperuser

Fase 7

Deploy na intranet

Colocar o sistema no ar dentro da rede interna, de forma que sobreviva a reinícios da VM e passe a se atualizar sozinho a cada git push, sem depender de alguém logado rodando runserver ou copiando arquivo manualmente.

Preparar o diretório de trabalho a partir do repositório bare

No servidor

O serviço vai servir esta pasta — ela precisa nascer como um checkout do repositório bare criado na Fase 0, não de um git clone externo. O usuário deploy precisa ter permissão de escrita aqui (mais simples: colocá-lo no mesmo grupo do dono da pasta).

git clone /home/deploy/rotinas-secretarias.git /home/usuario/apps/rotinas-secretarias
sudo usermod -aG usuario deploy   # ajuste "usuario" para o grupo real do dono da pasta

Instalar Gunicorn e configurar arquivos estáticos

No servidor 
pip install gunicorn
python manage.py collectstatic

Criar o serviço systemd

No servidor 
# /etc/systemd/system/rotinas.service
[Unit]
Description=Rotinas das Secretarias (Gunicorn)
After=network.target postgresql.service

[Service]
User=www-data
WorkingDirectory=/home/usuario/apps/rotinas-secretarias
ExecStart=/home/usuario/apps/rotinas-secretarias/.venv/bin/gunicorn \
    config.wsgi:application --bind 127.0.0.1:8000 --workers 3

Liberar o restart do serviço sem senha interativa

No servidor

O hook de deploy do próximo passo roda de forma não-interativa — sem isso, o git push ficaria travado esperando uma senha que ninguém vai digitar.

sudo visudo -f /etc/sudoers.d/deploy-rotinas
# adicionar a linha:
deploy ALL=(ALL) NOPASSWD: /bin/systemctl restart rotinas

Configurar o hook post-receive para deploy automático via git push

No servidor

Este script roda automaticamente toda vez que a máquina de dev der git push producao main: atualiza o diretório de trabalho, instala dependências novas, aplica migrations, coleta estáticos e reinicia o serviço. O git push passa a ser o deploy.

# /home/deploy/rotinas-secretarias.git/hooks/post-receive
#!/bin/bash
TARGET="/home/usuario/apps/rotinas-secretarias"
GIT_DIR="/home/deploy/rotinas-secretarias.git"
BRANCH="main"

while read oldrev newrev ref
do
  if [[ $ref = "refs/heads/$BRANCH" ]]; then
    echo "→ Deploy: atualizando $TARGET"
    git --work-tree="$TARGET" --git-dir="$GIT_DIR" checkout -f "$BRANCH"
    cd "$TARGET"
    source .venv/bin/activate
    pip install -r requirements.txt
    python manage.py migrate --noinput
    python manage.py collectstatic --noinput
    sudo systemctl restart rotinas
    echo "→ Deploy concluído: $(git --git-dir="$GIT_DIR" rev-parse --short "$newrev")"
  fi
done
sudo chmod +x /home/deploy/rotinas-secretarias.git/hooks/post-receive
Testar antes de confiarDa máquina de dev, rode git push producao main e acompanhe o output do hook no próprio terminal — ele aparece como se fosse parte da resposta do push.
