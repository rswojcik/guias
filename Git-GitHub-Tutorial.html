Controle de versão é a habilidade mais fundamental do desenvolvimento moderno. Este guia cobre tudo que você precisa para começar — do conceito ao comando.

O que é Git?

Git é um sistema de controle de versão distribuído. Ele registra cada mudança feita nos seus arquivos ao longo do tempo, permitindo que você volte a qualquer versão anterior, trabalhe em paralelo com outras pessoas e nunca perca trabalho.

Pense nele como um histórico completo e ramificável de tudo que aconteceu no seu projeto — quem mudou o quê, quando e por quê.

Por que usar controle de versão?

Sem Git

projeto-final.zip · projeto-final-v2.zip · projeto-AGORA-VAI.zip · projeto-final-MESMO.zip

Com Git

Um único repositório com histórico completo, rastreável, reversível e colaborativo.

Conceito central: Git não salva cópias inteiras dos arquivos a cada mudança — ele salva apenas as diferenças (diffs), tornando tudo extremamente eficiente.

Git vs GitHub

Essa é a confusão mais comum para quem está começando. São coisas distintas:

Aspecto Git GitHub
O que é Ferramenta de linha de comando Plataforma web (serviço online)
Onde roda Na sua máquina local Na nuvem (github.com)
Função Gerencia o histórico de versões Hospeda repositórios e facilita colaboração
Requer internet Não — funciona offline Sim
Alternativas Mercurial, SVN GitLab, Bitbucket, Azure DevOps
Resumo simples: Git é o motor. GitHub é a garagem onde você estaciona e compartilha o carro com outros.

Termos Essenciais

Esses são os termos que você vai encontrar no dia a dia. Memorize-os:

repository A pasta do projeto monitorada pelo Git. Contém todos os arquivos e o histórico completo de mudanças. Pode ser local (na sua máquina) ou remoto (no GitHub).
commit Um ponto de salvamento no histórico. Cada commit registra quais arquivos mudaram, quem fez a mudança, quando, e uma mensagem descrevendo o que foi feito.
branch Uma linha paralela de desenvolvimento. Permite trabalhar em funcionalidades novas sem afetar o código principal. A branch padrão geralmente se chama main ou master.
merge Unir o trabalho de uma branch com outra. Quando você termina uma funcionalidade, faz merge da sua branch de volta para a main.
clone Copiar um repositório remoto para a sua máquina. Feito uma vez por projeto. Traz todo o histórico junto.
push Enviar seus commits locais para o repositório remoto (ex: GitHub). Compartilha seu trabalho com o time.
pull Baixar e aplicar commits do repositório remoto na sua máquina. Mantém você atualizado com o que o time fez.
pull request (PR) Uma solicitação de revisão no GitHub. Você pede para que seu código em uma branch seja revisado e então mergeado na branch principal.
fork Cópia independente de um repositório de outra pessoa no GitHub. Permite contribuir com projetos onde você não tem permissão de acesso direto.
staging area Uma área intermediária (também chamada de index) onde você prepara as mudanças antes de commitar. Você escolhe quais arquivos entram no próximo commit.
conflict Quando duas pessoas editam o mesmo trecho de um arquivo e o Git não consegue decidir qual versão manter. Você precisa resolver manualmente.
.gitignore Arquivo de configuração que diz ao Git quais arquivos ignorar — como senhas, dependências (node_modules) e arquivos temporários.

Fluxo de Trabalho

O ciclo básico do Git tem quatro estados pelos quais seus arquivos passam:

✏️
Working Dir
→
📋
Staging Area
→
🗃️
Local Repo
→
☁️
Remote (GitHub)

O que acontece em cada etapa:

Working Directory Onde você edita os arquivos normalmente. O Git observa as mudanças mas ainda não as rastreia.
Staging Area Você usa git add para selecionar quais mudanças entrarão no próximo commit.
Local Repository Com git commit, as mudanças são salvas permanentemente no histórico local.
Remote Repository Com git push, seus commits vão para o GitHub, ficando acessíveis ao time.

Branches — Trabalhando em Paralelo

Branches são o coração do trabalho em equipe com Git. A ideia é simples: a branch main é o código estável, em produção. Para qualquer mudança, você cria uma branch separada, trabalha nela, e só junta de volta quando estiver pronto.

$ git branch # lista todas as branches $ git branch feature/login # cria uma nova branch $ git checkout feature/login # muda para essa branch # Atalho: criar e já mudar para a branch $ git checkout -b feature/login
Convenção de nomenclatura: Use prefixos para organizar — feature/ para novas funcionalidades, fix/ para correções de bugs, hotfix/ para correções urgentes em produção.

Comandos Básicos

Configuração inicial (apenas uma vez)

$ git config --global user.name "Seu Nome" $ git config --global user.email "seu@email.com"

Iniciando um projeto

# Opção 1: Novo repositório local $ git init # Opção 2: Clonar repositório existente do GitHub $ git clone https://github.com/usuario/repositorio.git

O ciclo diário

# Ver o estado atual dos arquivos $ git status # Adicionar arquivos ao staging $ git add arquivo.txt # arquivo específico $ git add . # todos os arquivos alterados # Criar um commit $ git commit -m "feat: adiciona tela de login" # Enviar para o GitHub $ git push origin main # Baixar atualizações do time $ git pull origin main

Inspecionando o histórico

$ git log --oneline # histórico compacto $ git diff # o que mudou mas ainda não está no staging $ git diff --staged # o que está no staging

Desfazendo mudanças

# Descartar mudanças no working directory $ git checkout -- arquivo.txt # Remover arquivo do staging (sem perder mudanças) $ git restore --staged arquivo.txt # Guardar mudanças temporariamente (útil ao trocar de branch) $ git stash $ git stash pop # recupera o que foi guardado
Cuidado: Evite usar git push --force em branches compartilhadas com o time. Isso reescreve o histórico remoto e pode apagar o trabalho de outras pessoas.

GitHub Flow — Colaboração na Prática

O GitHub Flow é o processo padrão de trabalho em equipe. São 6 etapas simples:

1. branch Crie uma branch com nome descritivo a partir da main. Ex: feature/relatorio-pdf
2. commit Faça commits pequenos e frequentes com mensagens claras. Prefira commits atômicos (uma mudança lógica por commit).
3. push Envie sua branch para o GitHub regularmente. Isso cria um backup e permite que o time acompanhe o progresso.
4. pull request Abra um Pull Request no GitHub descrevendo o que foi feito e por quê. Solicite revisão de um colega.
5. revisão O time revisa o código, deixa comentários. Você responde, ajusta, e faz novos commits na mesma branch.
6. merge Após aprovação, o PR é mergeado na main. A branch pode ser deletada. O ciclo recomeça.
Boas mensagens de commit: Use o formato tipo: descrição curta. Tipos comuns: feat (funcionalidade), fix (correção), docs (documentação), refactor, chore.

Cheatsheet

Referência rápida para consulta no dia a dia:

Setup
git init git clone <url> git config --global user.name "nome"
Commit
git status git add <arquivo> git commit -m "mensagem"
Branches
git branch <nome> git checkout -b <nome> git merge <branch>
Remoto
git push origin <branch> git pull origin <branch> git fetch
Histórico
git log --oneline git diff git show <commit-hash>
Desfazer
git stash git restore --staged <arquivo> git revert <commit>
