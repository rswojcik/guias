Pré-requisitos

O que verificar antes de começar a instalação

Windows compatível

O Claude Code roda nativamente no Windows — sem precisar de WSL. Confirme que seu sistema atende:

  • Windows 10 build 1809 ou superior, versão 64-bit
  • Windows 11 (qualquer edição)
  • Windows Server 2019 ou superior
🚨
Windows Server 2016 não é suportado oficialmente

A documentação lista Windows 10 1809+ ou Windows Server 2019+. Se o seu servidor é 2016, o mais seguro é instalar o Claude Code na sua estação de trabalho (Windows 10/11) e acessar o servidor remotamente (Invoke-Command, compartilhamentos de rede), em vez de rodar o agente dentro do servidor de produção.

⚠️
Atenção à versão do PowerShell

O PowerShell que vem instalado por padrão no Windows Server (2016/2019) é o 5.1. O Claude Code recomenda o PowerShell 7+ para melhor compatibilidade e detecção automática de shell.

Instalação do Claude Code

Instalação nativa no Windows via PowerShell

Método principal — Instalador nativo

Desde 2025, o Claude Code tem um instalador nativo para Windows. Não é mais necessário Node.js, npm ou WSL. O instalador baixa um único binário em %USERPROFILE%\.local\bin\claude.exe e mantém o Claude Code atualizado em background. Em alguns ambientes (como máquinas ingressadas em domínio) ele não adiciona essa pasta ao PATH — por isso o passo 4 abaixo.

  1. 1
    Abra o PowerShell 7 com o seu usuário normal

    Procure por pwsh no menu Iniciar e abra normalmente. Não é necessário executar como Administrador — e, se você elevar com outro usuário, o binário pode ser gravado no perfil dele, não no seu. Não use CMD ou Git Bash para este passo.

  2. 2
    Execute o instalador oficial 
    irm https://claude.ai/install.ps1 | iex

    O instalador baixa o binário para %USERPROFILE%\.local\bin.

  3. 3
    Teste se o claude é reconhecido 
    claude --version

    Se aparecer a versão, pule para o passo 5. Se aparecer "O termo 'claude' não é reconhecido…", o problema é o PATH — siga o passo 4.

  4. 4
    Diagnosticar e corrigir o PATH 
    PowerShell# 4a) Confirmar que o binário existe (deve retornar True)
Test-Path "$env:USERPROFILE\.local\bin\claude.exe"

# 4b) Testar rodando pelo caminho completo, sem mexer no PATH
& "$env:USERPROFILE\.local\bin\claude.exe" --version

# 4c) Verificar se a pasta já está no PATH (sem saída = não está)
$env:PATH -split ';' | Select-String '\.local\\bin'

# 4d) Adicionar a pasta ao PATH do usuário (permanente)
$currentPath = [Environment]::GetEnvironmentVariable('PATH', 'User')
[Environment]::SetEnvironmentVariable('PATH', "$currentPath;$env:USERPROFILE\.local\bin", 'User')

    Depois do 4d, feche e abra o PowerShell — janelas já abertas mantêm o PATH antigo.

    Se o Test-Path (4a) retornar False, rode echo $env:USERPROFILE para ver em qual perfil você está e refaça o passo 2 com o seu usuário normal, sem elevação.

  5. 5
    Verifique a instalação 
    claude --version
claude doctor    # diagnóstico completo do ambiente
⚠️
Execution Policy

Se o PowerShell bloquear a execução do script, rode uma vez: Set-ExecutionPolicy RemoteSigned -Scope CurrentUser

Método alternativo — WinGet

winget install Anthropic.ClaudeCode

# Atenção: WinGet não atualiza automaticamente.
# Para atualizar manualmente:
winget upgrade Anthropic.ClaudeCode

Integração com VS Code

Extensão oficial + CLI no terminal integrado — a combinação ideal

3.1 — Instalação e configuração inicial

  1. 1
    Instalar a extensão no VS Code

    Abra o VS Code → aba Extensões (Ctrl+Shift+X) → pesquise "Claude Code" → instale a extensão da Anthropic (publicador oficial).

  2. 2
    Posicionar o painel no secondary sidebar

    Arraste a aba do Claude para o lado direito da tela. Assim você vê o código no editor e o chat lado a lado, sem perder o contexto visual do arquivo que está editando.

  3. 3
    Autenticação

    A extensão usa a mesma conta que você autenticou via CLI. Se já fez o login no PowerShell, a extensão reconhece automaticamente. Caso contrário, um prompt de login abrirá no browser.

  4. 4
    Abrir o terminal integrado

    Use Ctrl+` para abrir o terminal integrado do VS Code. Dentro dele, rode claude. O Claude Code detecta automaticamente que está dentro de um workspace VS Code.

3.2 — Recursos da extensão

Diffs inline

Quando o Claude sugere uma mudança em um arquivo, ela aparece diretamente no editor — igual ao Git diff, com linhas vermelhas (removidas) e verdes (adicionadas). Você aceita ou rejeita arquivo por arquivo, bloco por bloco. Nada é alterado sem sua aprovação explícita.

@-mentions — referenciar arquivos e pastas

No campo de prompt da extensão, digite @ seguido do nome do arquivo ou pasta. O matching é fuzzy — você não precisa digitar o caminho completo:

# Exemplos de @-mentions na caixa de prompt:
@backup-script      # encontra backup-script.ps1
@src/scripts/       # inclui toda a pasta (barra no final)
@permissoes         # encontra qualquer arquivo com esse nome

# Atalho para @-mention com caminho e número de linha exatos:
Alt+K  (Windows/Linux)

Selection-aware context

Selecione qualquer trecho de código no editor antes de digitar o prompt. O rodapé da caixa de prompt mostra quantas linhas foram selecionadas, e o Claude as enxerga automaticamente — sem precisar copiar e colar.

✅
Uso prático para TI

Selecione um bloco de um script PowerShell problemático, abra o painel Claude, e escreva: "Este trecho está falhando com o erro X. Identifique o problema e corrija." O Claude já recebe o código selecionado.

Diagnósticos automáticos

A extensão lê os erros e warnings exibidos pelo VS Code (linter, PowerShell Extension, PSScriptAnalyzer). Quando você pergunta "por que este script está com erro?", o Claude já tem acesso a essas informações — você não precisa copiar mensagens de erro manualmente.

Checkpoints

Antes de qualquer mudança grande, o Claude Code cria um checkpoint automático — um ponto de restauração. Se a mudança não ficou boa, você pode desfazer tudo com um comando sem precisar do Git.

# Ver checkpoints disponíveis
/checkpoints

# Restaurar para um checkpoint específico
/restore checkpoint-id

Memória com CLAUDE.md

Contexto persistente que o Claude carrega automaticamente em cada sessão

4.1 — Por que isso existe

O Claude Code não tem memória entre sessões por padrão. Sem o CLAUDE.md, você começa cada conversa do zero: reexplicando que é um coordenador de TI, que o servidor roda Windows Server 2016, que existe uma GPO de folder redirection, que o grupo de corrida usa Supabase…

O CLAUDE.md é a solução: um arquivo Markdown que o Claude lê automaticamente ao iniciar qualquer sessão dentro de um projeto. É a "ficha de briefing" permanente do seu ambiente.

✅
Impacto real

Equipes que mantêm um CLAUDE.md bem estruturado reportam redução de 50%+ nos ciclos de correção — o Claude para de re-adivinhar o contexto e começa cada sessão já alinhado com as regras do projeto.

4.2 — A hierarquia de arquivos (5 níveis)

O Claude Code não lê apenas um CLAUDE.md — ele monta um contexto completo combinando até 5 níveis de arquivos. Os níveis mais específicos têm prioridade sobre os mais amplos.

G
~/.claude/CLAUDE.md
Global — vale para todos os projetos na sua máquina. Coloque aqui suas preferências pessoais: idioma de resposta, nível de detalhe, ferramentas que você usa.
P
/meu-projeto/CLAUDE.md
Projeto compartilhado — commitado no repositório. Vale para toda a equipe. Coloque aqui: ambiente do servidor, convenções, pastas proibidas, comandos frequentes.
A
/meu-projeto/.claude/CLAUDE.md
Alternativo de projeto — mesma função do anterior, mas mantém a raiz do projeto mais limpa. Escolha um ou outro, não os dois.
L
/meu-projeto/CLAUDE.local.md
Local pessoal — gitignored automaticamente. Apenas você vê este arquivo. Use para preferências que não devem valer para a equipe.
D
/meu-projeto/subpasta/CLAUDE.md
Diretório específico — carregado sob demanda (não na inicialização). Útil para regras que só valem para um módulo ou subprojeto específico.
💡
Como os níveis se combinam

Todos os arquivos são carregados e combinados — não se substituem. Em caso de conflito entre uma regra global e uma local, a mais específica vence. Pense como CSS: especificidade maior ganha.

4.3 — Sistema de regras com .claude/rules/

Para projetos maiores, em vez de colocar tudo em um único CLAUDE.md, você pode criar arquivos separados dentro da pasta .claude/rules/. Cada arquivo pode ter escopo de caminho próprio:

# Estrutura de exemplo para um projeto de TI:
.claude/
  rules/
    seguranca.md        # regras gerais de segurança
    scripts-ps1.md      # regras só para arquivos .ps1
    documentacao.md     # padrão de documentação
    backup.md           # regras para a pasta scripts/backup/

O cabeçalho de um arquivo de regra condicional por caminho:

---
paths:
  - "scripts/backup/**"
  - "scripts/manutencao/**"
---

# Regras para Scripts de Backup e Manutenção
- Sempre testar em ambiente de homologação antes de produção
- Nunca usar -Force sem confirmação explícita do usuário
- Registrar em log toda operação destrutiva (Remove-Item, Format-Volume)
✅
Regras sem paths

Arquivos de regra sem o campo paths: carregam incondicionalmente — valem para qualquer contexto do projeto, assim como o CLAUDE.md principal.

4.4 — Memória automática gerada pelo Claude

Além dos arquivos que você escreve, desde a versão 2.1.59 o Claude Code grava seus próprios aprendizados em uma pasta separada:

# Localização da memória automática:
~/.claude/projects/<nome-do-projeto>/memory/MEMORY.md

# O Claude carrega os primeiros 200 linhas (ou 25KB)
# deste arquivo a cada nova sessão.

# Para gerenciar, auditar ou desativar:
/memory
TipoQuem escreveLocalizaçãoConteúdo típico
CLAUDE.mdVocêPasta do projetoRegras, contexto, convenções
MEMORY.mdClaude Code~/.claude/projects/Aprendizados da sessão, correções que ele registrou
⚠️
Revise a memória automática periodicamente

Use /memory para auditar o que o Claude está gravando. Se ele aprendeu algo errado (ex: uma preferência temporária que não deveria persistir), corrija antes que afete sessões futuras.

4.5 — O que colocar (e o que não colocar)

✅ Coloque
O que pertence ao CLAUDE.md

Ambiente e versões do servidor, convenções de nomenclatura de arquivos, pastas ou sistemas que não devem ser tocados, comandos frequentes do seu ambiente, contexto dos projetos ativos, idioma de resposta preferido.

❌ Evite
O que não pertence

Instruções que mudam a cada sessão, conteúdo que poderia ir em um hook automatizado, informações óbvias demais, detalhes que só valem para uma conversa específica.

🚨
Limite de 200 linhas por arquivo

Modelos de linguagem conseguem seguir aproximadamente 100–150 instruções com qualidade. O sistema do Claude Code já consome ~50 instruções. Acima de 200 linhas, o CLAUDE.md começa a ser ignorado parcialmente. Seja conciso. Cada linha precisa justificar sua existência.

Importar arquivos externos

Para evitar duplicação, use a sintaxe @caminho/arquivo para importar outros arquivos dentro do CLAUDE.md. Suporta até 4 níveis de profundidade:

# No CLAUDE.md, você pode referenciar outros arquivos:
@docs/arquitetura-rede.md
@docs/convencoes-nomenclatura.md
@.claude/rules/seguranca.md

Abaixo, um modelo de CLAUDE.md global e outro de CLAUDE.local.md pensados para um coordenador de TI que também gerencia um grupo de corrida:

## Perfil

- Nível técnico: Intermediário/Avançado em infraestrutura Windows
- Idioma: Sempre responda em português brasileiro
- Preferência de resposta: Objetivo e prático. Sem rodeios.

## Ambiente principal
- SO: Windows Server 2016 Standard
- Shell: PowerShell 7+
- Gerenciamento: Active Directory, GPO, NTFS permissions
- IDE: VS Code com terminal integrado

## Preferências de comportamento
- Sempre use Plan Mode antes de sugerir mudanças destrutivas
- Prefiro ver exemplos de código antes de explicações longas
- Quando houver risco, destaque com um aviso claro antes de prosseguir
- Não sugira comandos Linux se houver alternativa nativa no PowerShell

## Projetos ativos
- Infraestrutura Windows Server (scripts de backup, GPO, AD)
- Grupo de corrida: frontend HTML/JS + Supabase + Cloudflare Pages

/projeto-infra/CLAUDE.md — Projeto de infraestrutura

# Projeto: Infraestrutura TI

## Ambiente
- Windows Server 2016 Standard (sem WSL, sem Linux)
- PowerShell 7.4+
- Active Directory com GPO de folder redirection ativa
- "Meus Documentos" redirecionado via GPO para \\servidor\usuarios\%USERNAME%

## Regras críticas
- NUNCA usar Remove-Item sem -WhatIf primeiro

- Estou usando VS Code com terminal integrado, não o PowerShell standalone
- Quando explicar algo técnico, use analogias de infraestrutura de rede

- Prefiro diffs compactos (não mostrar contexto além do necessário)

Criando Agentes

Do subagente simples ao time de agentes paralelos

5.1 — Conceitos fundamentais

Antes de criar agentes, é preciso entender o que cada modo significa na prática:

ModoO que éQuando usar
Sessão única Você + Claude em uma conversa linear. Um contexto, um fio de execução. Tarefas simples e rápidas do dia a dia
Subagente O Claude principal delega uma subtarefa para outra instância Claude — dentro da mesma sessão. O subagente começa com contexto limpo e isolado. Tarefas paralelas independentes (auditar N servidores ao mesmo tempo)
Agent Teams Múltiplas sessões Claude rodando em paralelo, coordenadas via workspace Git compartilhado. Cada instância é uma janela de terminal separada. Tarefas grandes demais para um único contexto
💡
O padrão central: Orquestrador → Subagentes

O orquestrador (agente principal) recebe a tarefa grande, quebra em subtarefas independentes, distribui para subagentes, coleta os resultados e sintetiza. O importante: subagentes não compartilham contexto entre si — cada um começa "do zero" com apenas o que o orquestrador enviou.

5.2 — Subagentes nativos do Claude Code

Não é preciso nenhuma configuração especial para usar subagentes. Basta pedir ao Claude para tratar partes independentes de uma tarefa em paralelo:

# Prompt para o orquestrador — ele cria os subagentes:
"Preciso auditar as permissões NTFS de 4 pastas de departamento:
D:\Dados\RH, D:\Dados\Financeiro, D:\Dados\TI, D:\Dados\Diretoria.

Para cada pasta, verifique:
- Quem tem acesso (usuários e grupos)
- Se há permissões herdadas inesperadas
- Se o grupo 'Domain Users' tem acesso indevido

Processe as 4 pastas em paralelo e consolide os resultados
em um relatório Markdown único."

O Claude cria subagentes para cada pasta, roda as verificações em paralelo e entrega um relatório consolidado — sem você precisar gerenciar as instâncias manualmente.

Casos de uso canônicos para TI

  • Auditar permissões NTFS de múltiplas pastas em paralelo
  • Revisar vários scripts PowerShell ao mesmo tempo
  • Pesquisar a causa de um erro em múltiplos logs simultaneamente
  • Gerar documentação de múltiplos módulos independentes
  • Verificar conectividade ou status de múltiplos servidores

5.3 — Definindo agentes customizados com AGENTS.md

Para criar agentes reutilizáveis com nome, ferramentas e comportamento definidos, use o arquivo AGENTS.md na raiz do projeto:

# AGENTS.md — na raiz do projeto

## security-auditor
description: Audita permissões NTFS e configurações de segurança.
  Leitura apenas — nunca modifica arquivos ou permissões.
model: claude-sonnet-4-6
tools:
  - Read
  - Bash(Get-Acl:*, Get-ADGroupMember:*, whoami:*)
behavior: |
  Você é um auditor de segurança. Seu trabalho é APENAS ler e
  reportar. Nunca execute comandos que modifiquem o sistema.
  Sempre apresente os resultados em tabelas Markdown.

---

## doc-writer
description: Gera e atualiza documentação técnica em Markdown.
  Só pode criar ou editar arquivos .md na pasta docs/.
model: claude-sonnet-4-6
tools:
  - Read
  - Write(docs/**/*.md)
behavior: |
  Você é um redator técnico. Gere documentação clara, objetiva
  e em português. Use headers, tabelas e blocos de código.
  Nunca toque em arquivos fora da pasta docs/.

---

## ps-reviewer
description: Revisa scripts PowerShell quanto a boas práticas,
  erros comuns e vulnerabilidades de segurança.
model: claude-sonnet-4-6
tools:
  - Read
behavior: |
  Revise scripts PowerShell e aponte: uso de -Force sem
  confirmação, falta de tratamento de erro (try/catch),
  credenciais hardcoded, e desvios do PSScriptAnalyzer.

Como invocar um agente customizado

# No prompt do Claude (terminal ou extensão VS Code):
"Spawn a teammate using the security-auditor agent
to audit D:\Dados\RH and report all permission issues."

"Use the doc-writer agent to generate documentation
for all scripts in scripts/backup/."

"Use the ps-reviewer agent to review scripts/manutencao/Clear-Logs.ps1."
✅
As definições do AGENTS.md são portáteis

Uma vez criadas, as definições funcionam em qualquer contexto do Claude Code — no terminal PowerShell, na extensão VS Code e em workflows automatizados. Defina uma vez, use sempre.

5.4 — Agent Teams (paralelismo avançado)

Agent Teams permite múltiplas instâncias do Claude Code rodando em paralelo e se comunicando — cada uma em uma janela de terminal separada, coordenadas por um workspace Git compartilhado.

💡
Lançado em fevereiro de 2026 (v2.1.32)

Disponível como research preview. Ideal para tarefas com escopo grande demais para um único contexto de 200k tokens — como documentar toda a infraestrutura de um servidor complexo.

Configuração recomendada no Windows Terminal

# settings.json do Windows Terminal — 5 abas de PowerShell na inicialização:
{
  "startupActions": "new-tab -p \"PowerShell\" ;
    new-tab -p \"PowerShell\" ;
    new-tab -p \"PowerShell\" ;
    new-tab -p \"PowerShell\" ;
    new-tab -p \"PowerShell\""
}

Em cada aba: uma instância de Claude Code rodando um agente diferente. O orquestrador (aba 1) distribui tarefas e os agentes (abas 2–5) executam em paralelo.

Como os agentes se comunicam

MecanismoComo funciona
SendMessageCada agente tem um "mailbox". O orquestrador envia mensagens com contexto e instruções.
Lista de tarefasArquivo de tarefas compartilhado via Git. Agentes marcam tarefas como concluídas.
Git workspaceArquivos produzidos por um agente ficam disponíveis para os outros via repositório compartilhado.

# Aba 1 — Orquestrador:

5.5 — Workflows determinísticos

Workflows são um nível acima dos subagentes: em vez do Claude decidir o fluxo de execução a cada turno, você define o fluxo em código (JavaScript) e os agentes executam dentro desse fluxo previsível.

O padrão universal: fan-out → verificação → síntese

# Acompanhar workflows em execução:
/workflows   # mostra progresso em tempo real de cada agente

Exemplo de workflow para TI — Relatório de backup consolidado

// .claude/workflows/relatorio-backup.js
// Padrão: fan-out → verificação → síntese

const servidores = ['SRV-01', 'SRV-02', 'SRV-03'];

// Fan-out: 3 agentes lendo logs em paralelo
const resultados = await parallel(
  servidores.map(srv => agent({
    prompt: `Leia o log de backup de ${srv} dos últimos 7 dias.
      Retorne: status (OK/FALHA), tamanho total, erros encontrados.`,
    tools: ['Read'],
    schema: BackupReportSchema // JSON estruturado
  }))
);

// Síntese: um agente consolida e gera o relatório
await agent({
  prompt: `Consolide estes relatórios de backup em um único
    documento Markdown com tabela resumo e alertas de falha:
    ${JSON.stringify(resultados)}`,
  tools: ['Write'],
  output: 'docs/relatorio-backup-semanal.md'
});
✅
Quando usar workflows vs subagentes simples

Subagentes simples (pedir ao Claude para fazer N coisas em paralelo) cobrem 80% dos casos. Workflows são para quando você quer controle preciso do fluxo — sequenciamento, verificação cruzada entre agentes, ou tarefas que se repetem regularmente com o mesmo padrão.

5.6 — Segurança e permissões ao usar agentes

Agentes executando de forma autônoma em um ambiente de produção exigem cuidado. Nunca dar permissão irrestrita a agentes que acessam servidores com dados reais.

Hook de proteção via PowerShell

# .claude/hooks/block-dangerous-command.ps1
# Bloqueia comandos destrutivos antes que o agente os execute

param([string]$Command)

$blocklist = @(
    'Remove-Item',
    'Format-Volume',
    'Clear-Disk',
    'Stop-Service',
    'Restart-Computer'
)

foreach ($cmd in $blocklist) {
    if ($Command -match $cmd) {
        Write-Error "BLOQUEADO: '$cmd' requer aprovação manual."
        exit 1
    }
}

exit 0  # Comando aprovado

Registrar o hook no projeto

# .claude/settings.json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash|PowerShell",
      "hooks": [{
        "type": "command",
        "command": "powershell.exe -NoProfile -ExecutionPolicy Bypass -File \".claude\\hooks\\block-dangerous-command.ps1\"",
        "shell": "powershell"
      }]
    }]
  }
}

Boas práticas de segurança com agentes

  • Use Plan Mode sempre — antes de qualquer automação nova, peça /plan e leia o plano antes de aprovar a execução
  • Allowlists no AGENTS.md — defina exatamente quais comandos cada agente pode executar (ex: Bash(Get-Acl:*) — só leitura de ACL)
  • Sandbox primeiro — teste agentes em pasta de homologação antes de liberar no ambiente real
  • Agentes de leitura vs escrita — separe agentes que só leem (auditoria) dos que escrevem (documentação, correção). Dê permissão mínima necessária
  • Revise diffs antes de aprovar — mesmo em tarefas automatizadas, leia o diff gerado antes de aceitar
🚨
Nunca use --dangerously-skip-permissions em produção

Esta flag remove todas as verificações de segurança do Claude Code. Pode ser útil em ambientes completamente isolados e controlados, mas jamais em servidores com dados reais ou credenciais de produção.

Checklist de segurança antes de ativar um agente

  • ☐ O agente tem apenas as ferramentas que precisa (mínimo necessário)
  • ☐ O hook de bloqueio de comandos destrutivos está ativo
  • ☐ Testei em ambiente de homologação
  • ☐ Tenho backup recente do ambiente que o agente vai acessar
  • ☐ Plan Mode foi revisado e aprovado antes da execução
  • ☐ Sei como revogar o acesso do agente rapidamente se algo sair errado
Próximos passos recomendados
  1. Instale o Claude Code via PowerShell (usuário normal, sem admin), teste o PATH com claude --version e rode claude doctor para validar o ambiente
  2. Crie seu ~/.claude/CLAUDE.md global com seu contexto de TI e preferências de resposta
  3. Instale a extensão VS Code e configure o painel no secondary sidebar
  4. Crie o CLAUDE.md do projeto de infraestrutura com as regras críticas do seu ambiente
  5. Experimente seu primeiro agente: peça ao Claude para auditar permissões de 3 pastas em paralelo
  6. Crie seu AGENTS.md com o security-auditor e o doc-writer e valide em homologação
