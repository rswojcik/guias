1. Como usar este guia e o que será montado

Execute as etapas na ordem. Cada etapa explica o objetivo, apresenta os comandos, diz o que você deve ver e termina com uma validação. Marque a caixa da etapa somente depois de confirmar o resultado.

Os comandos são executados no terminal do servidor Linux (via SSH ou console do Proxmox), salvo quando indicarem PowerShell do seu computador. Substitua todos os valores entre sinais de maior/menor, como <IP_VM_BANCO>, antes de executar. Não cole os sinais de maior/menor literalmente.

5. Primeiro acesso, atualização e ajustes básicos

Executar em: vm-apps e vm-banco

5.1 Conectar pelo SSH

No PowerShell do seu computador:

ssh <SEU_USUARIO>@<IP_DA_VM>

Na primeira conexão, responda yes para registrar a identidade do servidor. Se você importou a chave do GitHub, o acesso acontece sem senha (pode pedir a frase-senha da sua chave).

5.2 Atualizar o sistema e instalar ferramentas básicas

sudo apt update
sudo apt full-upgrade -y
sudo apt install -y ca-certificates curl gnupg git unzip jq htop qemu-guest-agent

O sudo executa o comando como administrador e pede a sua senha. apt update atualiza a lista de pacotes; full-upgrade instala as atualizações.

5.3 Fuso horário e relógio

sudo timedatectl set-timezone America/Sao_Paulo
timedatectl status

Resultado esperado: Time zone: America/Sao_Paulo e System clock synchronized: yes. Relógio correto é essencial para HTTPS, logs e backups.

5.4 Ativar o agente do Proxmox

sudo systemctl start qemu-guest-agent
systemctl status qemu-guest-agent --no-pager

Se o status indicar que o dispositivo não existe, a opção Qemu Agent não estava marcada na criação da VM: marque em Options → QEMU Guest Agent no Proxmox e faça um desligamento completo (sudo poweroff e depois Start). Um simples reboot não aplica essa mudança. Validação: no Proxmox, a aba Summary da VM passa a mostrar os IPs.

5.5 Conferir o disco

df -h /
sudo vgs

Se o df mostrar um tamanho bem menor que o disco criado e a coluna VFree do vgs tiver espaço livre, expanda o volume para usar tudo:

sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
df -h /

5.6 Registrar os nomes das VMs

Para que uma VM encontre a outra pelo nome, acrescente as duas no arquivo /etc/hosts:

echo "<IP_VM_APPS>   vm-apps"  | sudo tee -a /etc/hosts
echo "<IP_VM_BANCO>  vm-banco" | sudo tee -a /etc/hosts
ping -c 3 vm-banco
ping -c 3 vm-apps

5.7 Reiniciar se necessário

[ -f /var/run/reboot-required ] && echo "REINICIAR" || echo "Não precisa reiniciar"

Se aparecer REINICIAR, execute sudo reboot, aguarde um minuto e conecte novamente.

6. Conferir o IP fixo (netplan)

Executar em: vm-apps e vm-banco, pelo console do Proxmox

Se você configurou o IP manual no instalador, esta etapa é só conferência. Execute pelo console do Proxmox: se algo der errado na rede, o SSH cai, mas o console continua funcionando.

ip -br address
ip route
ls /etc/netplan/
sudo cat /etc/netplan/*.yaml

Confirme o IP esperado na placa (ens18), a rota default via <GATEWAY> e, no arquivo, dhcp4: false ou a ausência de dhcp4: true.

Se o IP estiver por DHCP, configure manualmente

Impeça o cloud-init de reescrever a rede e edite o arquivo:

echo "network: {config: disabled}" | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
sudo nano /etc/netplan/50-cloud-init.yaml

Conteúdo (a indentação com espaços é obrigatória; nunca use Tab):

network:
  version: 2
  ethernets:
    ens18:
      dhcp4: false
      addresses:
        - <IP_DA_VM>/<PREFIXO>
      routes:
        - to: default
          via: <GATEWAY>
      nameservers:
        addresses: [<DNS>, 1.1.1.1]
sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan try

O netplan try aplica a configuração e espera você pressionar Enter para confirmar. Se a rede quebrar e você não confirmar, ele desfaz sozinho em 120 segundos. Depois, teste:

ping -c 3 <GATEWAY>
ping -c 3 ubuntu.com

7. Proteger o acesso SSH

Executar em: vm-apps e vm-banco

7.1 Garantir que sua chave está instalada

Se você não importou a chave do GitHub na instalação, copie-a agora. No PowerShell do seu computador:

Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | ssh <SEU_USUARIO>@<IP_DA_VM> "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Em uma nova janela do PowerShell, conecte novamente. Se entrar sem pedir a senha do servidor (apenas a frase-senha da chave, se houver), a chave funciona. Não avance sem isso.

7.2 Desativar login por senha e do root

Em vez de alterar o arquivo principal, crie um arquivo próprio de configuração. O SSH lê os arquivos da pasta sshd_config.d em ordem alfabética e usa o primeiro valor que encontra, por isso o nome começa com 10-: ele vence o arquivo 50-cloud-init.conf, que às vezes liga o login por senha.

sudo nano /etc/ssh/sshd_config.d/10-seguranca.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
X11Forwarding no
sudo sshd -t
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|pubkeyauthentication)'
sudo systemctl restart ssh

O sshd -t não deve mostrar nada (sem erros). O sshd -T deve mostrar permitrootlogin no, passwordauthentication no e pubkeyauthentication yes.

Mantenha a sessão atual aberta e teste uma nova conexão em outra janela antes de fechar qualquer coisa. Se a nova conexão falhar, use o console do Proxmox, apague o arquivo com sudo rm /etc/ssh/sshd_config.d/10-seguranca.conf e reinicie o SSH.

8. Atualizações automáticas, fail2ban e snapshot da base

Executar em: vm-apps e vm-banco

8.1 Atualizações de segurança automáticas

sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

Responda Sim. Confirme o resultado:

cat /etc/apt/apt.conf.d/20auto-upgrades

Deve conter APT::Periodic::Update-Package-Lists "1"; e APT::Periodic::Unattended-Upgrade "1";. As atualizações de segurança passam a ser instaladas diariamente. O servidor não reinicia sozinho; a rotina da etapa 25 cuida disso.

8.2 fail2ban: bloquear tentativas repetidas de login

sudo apt install -y fail2ban
sudo nano /etc/fail2ban/jail.local
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
backend = systemd
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

Resultado esperado: Status for the jail: sshd com os contadores de falhas e bloqueios. Se um dia você bloquear o próprio IP, entre pelo console do Proxmox e execute sudo fail2ban-client set sshd unbanip <SEU_IP>.

8.3 Snapshot da base pronta

No Proxmox, selecione a VM → Snapshots → Take Snapshot, com o nome base-pronta. Se algo der muito errado nas próximas etapas, você volta a este ponto em vez de reinstalar.

Snapshot não é backup: ele fica no mesmo armazenamento da VM e deixa a VM mais lenta se acumular. Apague snapshots antigos depois que tudo estiver funcionando. O backup de verdade é o Proxmox Backup Server: confirme em Datacenter → Backup que existe um job incluindo as duas VMs.

9. Firewall da vm-banco

Executar em: vm-banco

A vm-banco aceita só duas coisas: SSH vindo da rede interna e PostgreSQL vindo exclusivamente da vm-apps. Todo o resto é bloqueado.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <REDE_INTERNA> to any port 22 proto tcp comment 'SSH rede interna'
sudo ufw allow from <IP_VM_APPS> to any port 5432 proto tcp comment 'PostgreSQL vm-apps'
sudo ufw show added
sudo ufw enable
sudo ufw status verbose

O ufw show added mostra as regras antes de ativar: confira se a regra de SSH está lá. Ao ativar, confirme com y. Teste uma nova conexão SSH em outra janela.

Se você administra de uma rede diferente (por exemplo, via VPN com outra faixa de IPs), inclua essa faixa na regra de SSH antes do ufw enable, ou você perderá o acesso remoto. Nesse caso, use o console do Proxmox e sudo ufw disable para corrigir.

10. Instalar o PostgreSQL

Executar em: vm-banco

sudo apt install -y postgresql
sudo systemctl status postgresql --no-pager
ls /etc/postgresql/

O último comando mostra a versão principal instalada (por exemplo 18). Ela é usada nos caminhos dos arquivos de configuração. Para não precisar digitar, guarde-a numa variável da sessão:

PGVER=$(ls /etc/postgresql/)
echo "Versão do PostgreSQL: $PGVER"
sudo -u postgres psql -c "SELECT version();"
sudo -u postgres psql -c "SHOW ssl;"

O SHOW ssl deve mostrar on: o Ubuntu já ativa a criptografia com um certificado gerado na instalação. A conexão entre as VMs será cifrada.

Sobre o sudo -u postgres: a instalação cria o usuário de sistema postgres, que é o administrador do banco. Esse prefixo executa o comando como ele. A variável PGVER vale só para a sessão atual: se reconectar, execute de novo a linha PGVER=$(ls /etc/postgresql/).

11. Permitir conexões da vm-apps

Executar em: vm-banco

Por padrão, o PostgreSQL só aceita conexões da própria máquina. São duas configurações: onde ele escuta e quem pode entrar.

11.1 Escutar também no IP da rede interna

O arquivo principal do Ubuntu inclui automaticamente os arquivos da pasta conf.d. Crie um arquivo próprio lá, sem mexer no principal:

sudo nano /etc/postgresql/$PGVER/main/conf.d/10-rede.conf
listen_addresses = 'localhost,<IP_VM_BANCO>'
password_encryption = 'scram-sha-256'

11.2 Definir quem pode entrar (pg_hba.conf)

O pg_hba.conf é a lista de acesso do banco. Cada linha diz: tipo de conexão, qual banco, qual usuário, de qual IP e como autenticar.

sudo cp -a /etc/postgresql/$PGVER/main/pg_hba.conf /etc/postgresql/$PGVER/main/pg_hba.conf.original
sudo nano /etc/postgresql/$PGVER/main/pg_hba.conf

Vá até o final do arquivo e acrescente uma linha por aplicação:

# Aplicações na vm-apps — somente cifrado (hostssl), somente o IP da vm-apps
# TIPO     BANCO        USUARIO        ENDERECO            METODO
hostssl    estoque_db   estoque_user   <IP_VM_APPS>/32     scram-sha-256
CampoSignificado
hostsslAceita só conexões de rede cifradas. Conexões sem criptografia são recusadas.
estoque_db / estoque_userEsse usuário só entra nesse banco. Uma aplicação não acessa o banco da outra.
<IP_VM_APPS>/32O /32 significa exatamente um IP, o da vm-apps.
scram-sha-256Autenticação por senha com o método seguro atual.

11.3 Aplicar e conferir

sudo systemctl restart postgresql
sudo systemctl status postgresql --no-pager
sudo ss -lntp | grep 5432

Resultado esperado: o PostgreSQL escutando em 127.0.0.1:5432 e em <IP_VM_BANCO>:5432. Se o serviço não subir, veja o motivo com sudo journalctl -u postgresql@$PGVER-main -n 50 --no-pager.

Mudanças no listen_addresses exigem restart. Mudanças apenas no pg_hba.conf (como adicionar uma aplicação nova) só precisam de sudo systemctl reload postgresql, que não derruba conexões.

12. Criar o banco e o usuário de cada aplicação

Executar em: vm-banco

12.1 Gerar uma senha forte

openssl rand -base64 48 | tr -dc 'A-Za-z0-9' | head -c 32; echo

A senha gerada tem só letras e números, o que evita problemas ao colocá-la no endereço de conexão. Copie e guarde no cofre de senhas com o nome da aplicação.

12.2 Criar usuário e banco

sudo -u postgres createuser --pwprompt --no-createdb --no-createrole --no-superuser estoque_user
sudo -u postgres createdb --owner=estoque_user estoque_db
sudo -u postgres psql -c "REVOKE CONNECT ON DATABASE estoque_db FROM PUBLIC;"

O --pwprompt pede a senha duas vezes (cole a senha gerada). Digitando a senha no prompt, ela não fica gravada no histórico do terminal. O REVOKE impede que outros usuários do banco se conectem a esse banco.

12.3 Conferir

sudo -u postgres psql -c "\du"
sudo -u postgres psql -c "\l"

O \du lista os usuários: estoque_user deve aparecer sem atributos de superusuário. O \l lista os bancos: estoque_db com dono estoque_user.

Se a aplicação já tem dados no seu computador que precisam ir para o servidor, gere um arquivo com pg_dump -Fc -f estoque.dump <banco_local> no seu computador, copie para a vm-banco com scp estoque.dump <SEU_USUARIO>@<IP_VM_BANCO>:/tmp/ e restaure com sudo -u postgres pg_restore --no-owner --role=estoque_user -d estoque_db /tmp/estoque.dump. Apague o arquivo de /tmp depois.

13. Backup diário dos bancos com pg_dump

Executar em: vm-banco

O Proxmox Backup Server copia a VM inteira. O pg_dump complementa: gera um arquivo por banco, permitindo restaurar uma única aplicação sem voltar a VM toda e sem perder os dados das outras.

13.1 Criar a pasta e o script

sudo install -d -o postgres -g postgres -m 700 /var/backups/postgresql
sudo nano /usr/local/bin/backup-postgres.sh
#!/usr/bin/env bash
# Backup lógico diário de todos os bancos do PostgreSQL
set -euo pipefail

DESTINO="/var/backups/postgresql"
RETENCAO_DIAS=14
DATA=$(date +%F_%H%M)

cd "$DESTINO"

BANCOS=$(psql -AtX -c "SELECT datname FROM pg_database WHERE datallowconn AND NOT datistemplate AND datname <> 'postgres';")

for BANCO in $BANCOS; do
  echo "Copiando $BANCO..."
  pg_dump -Fc -f "${DESTINO}/${BANCO}_${DATA}.dump" "$BANCO"
done

# Usuários e permissões (não fazem parte do pg_dump de cada banco)
pg_dumpall --globals-only -f "${DESTINO}/globais_${DATA}.sql"

# Apaga cópias mais antigas que a retenção
find "$DESTINO" -type f \( -name '*.dump' -o -name '*.sql' \) -mtime +"$RETENCAO_DIAS" -delete

echo "Backup concluído em $(date)"
sudo chmod 750 /usr/local/bin/backup-postgres.sh
sudo chown root:postgres /usr/local/bin/backup-postgres.sh

13.2 Agendar com o systemd

Crie o serviço, que diz o que executar:

sudo nano /etc/systemd/system/backup-postgres.service
[Unit]
Description=Backup lógico diário do PostgreSQL
After=postgresql.service

[Service]
Type=oneshot
User=postgres
Group=postgres
ExecStart=/usr/local/bin/backup-postgres.sh

E o timer, que diz quando executar:

sudo nano /etc/systemd/system/backup-postgres.timer
[Unit]
Description=Agenda o backup diário do PostgreSQL

[Timer]
OnCalendar=*-*-* 01:30:00
Persistent=true

[Install]
WantedBy=timers.target
sudo systemctl daemon-reload
sudo systemctl enable --now backup-postgres.timer
systemctl list-timers backup-postgres.timer

O Persistent=true faz o backup rodar assim que a VM ligar, caso ela estivesse desligada no horário. Configure o job do Proxmox Backup Server para depois das 01:30 (por exemplo 02:30): assim o backup da VM já leva os arquivos do dia.

13.3 Testar agora e testar a restauração

sudo systemctl start backup-postgres.service
sudo journalctl -u backup-postgres.service -n 20 --no-pager
sudo ls -lh /var/backups/postgresql/

Um backup só vale se a restauração funciona. Teste restaurando num banco temporário:

ARQUIVO=$(sudo ls -t /var/backups/postgresql/estoque_db_*.dump | head -1)
sudo -u postgres createdb teste_restauracao
sudo -u postgres pg_restore --no-owner -d teste_restauracao "$ARQUIVO"
sudo -u postgres psql -d teste_restauracao -c "\dt"
sudo -u postgres dropdb teste_restauracao

Com o banco ainda vazio, o \dt pode não listar tabelas. Repita este teste depois que a aplicação estiver em uso: as tabelas dela devem aparecer.

14. Firewall da vm-apps

Executar em: vm-apps

A vm-apps recebe SSH da rede interna e HTTP/HTTPS de qualquer lugar. As portas das aplicações (3001, 3002...) não são abertas: só o Nginx fala com elas, dentro da própria VM.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <REDE_INTERNA> to any port 22 proto tcp comment 'SSH rede interna'
sudo ufw allow 80/tcp comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'

Teste uma nova conexão SSH em outra janela antes de fechar a atual.

16. Criar o usuário das aplicações e instalar o PM2

Executar em: vm-apps

As aplicações não rodam com a sua conta nem como root. Elas rodam com o usuário apps, sem senha e sem permissão de administrador. Se uma aplicação for invadida, o estrago fica limitado a esse usuário.

16.1 Usuário e pasta

sudo adduser --disabled-password --gecos "" apps
sudo install -d -o apps -g apps -m 755 /srv/apps
sudo install -d -o apps -g apps -m 755 /srv/apps/bin

O --disabled-password impede login com senha. Para trabalhar como apps, a partir da sua conta, use:

sudo -iu apps       # entra como apps
whoami              # deve mostrar: apps
exit                # volta para sua conta

16.2 PM2

O PM2 mantém as aplicações Node.js rodando, reinicia se caírem, guarda os logs e sobe tudo quando o servidor liga.

sudo npm install -g pm2
pm2 -v
sudo pm2 startup systemd -u apps --hp /home/apps
systemctl status pm2-apps --no-pager

O comando pm2 startup cria o serviço pm2-apps, que inicia o PM2 do usuário apps no boot. Ele pode aparecer como inactive até existir a primeira aplicação salva, na etapa 18.

16.3 Rotação de logs

Sem rotação, os logs crescem até encher o disco:

sudo -iu apps
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 10M
pm2 set pm2-logrotate:retain 14
pm2 set pm2-logrotate:compress true
exit

18. Configurar e iniciar uma aplicação Node.js

Executar em: vm-apps, como usuário apps

18.1 Descobrir como a aplicação inicia

sudo -iu apps
cd /srv/apps/estoque
cat package.json | jq '.main, .scripts'

Procure o arquivo principal: o campo main ou o comando do script start (por exemplo node server.js ou node src/index.js). Anote o caminho do arquivo.

18.2 A aplicação deve escutar só em 127.0.0.1

Verifique no código onde a aplicação chama listen. O ideal é:

const PORT = process.env.PORT || 3001;
app.listen(PORT, '127.0.0.1', () => console.log(`Rodando na porta ${PORT}`));

Informar '127.0.0.1' faz a aplicação aceitar conexões só de dentro da VM, ou seja, só do Nginx. O firewall já bloqueia a porta, mas essa é uma segunda camada. Se precisar alterar, faça no seu computador, commit, push e git pull aqui.

18.3 Criar o .env

cp .env.example .env
nano .env
chmod 600 .env

Preencha com os valores reais. Exemplo:

NODE_ENV=production
PORT=3001
DATABASE_URL=postgres://estoque_user:<SENHA_DO_COFRE>@<IP_VM_BANCO>:5432/estoque_db?sslmode=no-verify
Sobre o sslmode: o certificado do PostgreSQL é gerado pelo próprio Ubuntu, não por uma autoridade reconhecida. Com a biblioteca pg (node-postgres), use sslmode=no-verify: a conexão continua cifrada, só não valida a identidade do certificado, o que é aceitável dentro da rede interna com firewall liberando apenas a vm-apps. Com Prisma ou outras bibliotecas, use sslmode=require. Se aparecer erro self-signed certificate, é esse ajuste que falta.

18.4 Instalar dependências

npm ci --omit=dev

O npm ci exige o package-lock.json e instala exatamente as versões registradas. O --omit=dev deixa de fora ferramentas de desenvolvimento. Se a aplicação tem um passo de criação de tabelas (migrations ou um arquivo .sql), execute agora, conforme o README dela.

18.5 Arquivo de configuração do PM2

Um único arquivo descreve todas as aplicações Node.js do servidor:

nano /srv/apps/ecosystem.config.cjs
module.exports = {
  apps: [
    {
      name: "estoque",
      cwd: "/srv/apps/estoque",
      script: "server.js",            // arquivo principal descoberto em 18.1
      node_args: "--env-file=.env",   // Node lê o .env da pasta da aplicação
      instances: 1,
      autorestart: true,
      max_memory_restart: "400M",     // reinicia se passar desse consumo
      time: true                      // data e hora em cada linha de log
    }
    // próximas aplicações entram aqui, separadas por vírgula
  ]
};

18.6 Iniciar, testar e salvar

pm2 start /srv/apps/ecosystem.config.cjs
pm2 status
pm2 logs estoque --lines 30 --nostream
curl -i http://127.0.0.1:3001/
pm2 save
exit

Resultado esperado: pm2 status com estoque em online e o curl retornando uma resposta HTTP (200, ou 302 se a aplicação redireciona para login). O pm2 save grava a lista atual para ser restaurada no boot.

Se o status ficar alternando entre online e errored com o contador de reinícios (↺) subindo, a aplicação está travando ao iniciar. Leia pm2 logs estoque --lines 50 --nostream: normalmente é variável faltando no .env, caminho errado em script ou falha de conexão com o banco.

19. Instalar e configurar o Nginx

Executar em: vm-apps

19.1 Instalar e ajustes gerais

sudo apt install -y nginx
sudo nano /etc/nginx/conf.d/00-geral.conf
# Não revela a versão do Nginx nas respostas e páginas de erro
server_tokens off;

# Suporte a WebSocket nas aplicações que usarem
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

19.2 Recusar acessos sem nome conhecido

Substitua o site padrão por um que encerra conexões para nomes que não são das suas aplicações (robôs que varrem IPs da internet):

sudo rm /etc/nginx/sites-enabled/default
sudo nano /etc/nginx/sites-available/00-bloqueio
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;
    return 444;
}
sudo ln -s /etc/nginx/sites-available/00-bloqueio /etc/nginx/sites-enabled/

19.3 Site da aplicação Node.js (proxy)

sudo nano /etc/nginx/sites-available/estoque
server {
    listen 80;
    listen [::]:80;
    server_name estoque.<DOMINIO>;

    access_log /var/log/nginx/estoque.access.log;
    error_log  /var/log/nginx/estoque.error.log;

    # Tamanho máximo de upload
    client_max_body_size 20m;

    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        $connection_upgrade;
        proxy_read_timeout 60s;
    }
}
Se a aplicação usa Express e precisa saber o IP real do usuário ou se a conexão é HTTPS (por exemplo, para cookies seguros), adicione no código app.set('trust proxy', 1);. Os cabeçalhos X-Forwarded-* acima passam essas informações.

19.4 Site da aplicação estática

sudo nano /etc/nginx/sites-available/portal
server {
    listen 80;
    listen [::]:80;
    server_name portal.<DOMINIO>;

    access_log /var/log/nginx/portal.access.log;
    error_log  /var/log/nginx/portal.error.log;

    root /srv/apps/portal;     # pasta onde está o index.html
    index index.html;

    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # Bloqueia arquivos ocultos, como a pasta .git e o .env
    location ~ /\. {
        deny all;
    }

    location / {
        try_files $uri $uri/ =404;
    }
}
Não remova o bloqueio de arquivos ocultos. A pasta foi clonada do GitHub e contém a pasta .git. Sem esse bloqueio, qualquer pessoa poderia baixar todo o histórico do código pelo navegador. Se o index.html ficar numa subpasta (como public ou dist), aponte o root para ela: fica ainda mais seguro.

Se o portal for uma aplicação de página única (React, Vue etc.) que controla as rotas no navegador, troque o try_files por try_files $uri $uri/ /index.html;.

19.5 Ativar os sites e testar

sudo ln -s /etc/nginx/sites-available/estoque /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/portal  /etc/nginx/sites-enabled/
sudo -u www-data test -r /srv/apps/portal/index.html && echo "Nginx consegue ler o portal"
sudo nginx -t
sudo systemctl reload nginx

O nginx -t deve terminar com syntax is ok e test is successful. Sempre rode o teste antes do reload: com erro de configuração, o Nginx recusa a recarga e continua com a versão anterior. Teste de dentro da VM, simulando o nome de cada site:

curl -i -H "Host: estoque.<DOMINIO>" http://127.0.0.1/
curl -i -H "Host: portal.<DOMINIO>"  http://127.0.0.1/
curl -i -H "Host: portal.<DOMINIO>"  http://127.0.0.1/.git/config
curl -i http://127.0.0.1/

Resultados esperados: os dois primeiros respondem as aplicações; o terceiro retorna 403 Forbidden (bloqueio funcionando); o último não retorna nada (Empty reply from server), pois não informa nome conhecido.

21. DNS e redirecionamento de portas no roteador

Executar em: painel de DNS do domínio e roteador

21.1 Confirmar o IP público

curl -4 -s https://ifconfig.me; echo

Compare com o IP informado pelo provedor. Ele precisa ser fixo: se mudar, os endereços param de funcionar. Se o seu IP for dinâmico, use um serviço de DNS dinâmico ou o Cloudflare Tunnel (que publica sem depender de IP fixo nem de portas abertas); trate isso antes de seguir.

21.2 Criar os registros DNS

No painel de DNS do domínio, crie um registro para cada aplicação:

TipoNomeValorTTL
AestoqueIP público da empresa3600 (ou o padrão)
AportalIP público da empresa3600 (ou o padrão)

Verifique a propagação (pode levar de minutos a algumas horas):

resolvectl query estoque.<DOMINIO>
resolvectl query portal.<DOMINIO>

21.3 Redirecionar as portas no roteador

No roteador ou firewall da borda, crie o encaminhamento (Port Forwarding / NAT / Virtual Server):

Porta externaProtocoloDestino internoPorta interna
80TCP<IP_VM_APPS>80
443TCP<IP_VM_APPS>443
Encaminhe só essas duas portas, só para a vm-apps. Nunca encaminhe 22 (SSH), 5432 (PostgreSQL) nem as portas das aplicações. A vm-banco nunca deve ficar alcançável pela internet.

21.4 Testar de fora

Desligue o Wi-Fi do celular e, usando a rede móvel, abra http://estoque.<DOMINIO>. A aplicação deve aparecer (ainda sem HTTPS).

Funciona no celular, mas não dentro da empresa? Muitos roteadores não permitem que um computador da rede interna acesse o próprio IP público (recurso chamado NAT loopback ou hairpin NAT). A solução é ativar esse recurso no roteador ou configurar o DNS interno da empresa para que os subdomínios apontem direto para <IP_VM_APPS>.

22. Ativar o HTTPS com Certbot

Executar em: vm-apps

O Certbot obtém certificados gratuitos do Let's Encrypt, configura o Nginx e renova automaticamente. Ele precisa que o DNS já aponte para a empresa e que a porta 80 esteja acessível pela internet (etapa 21).

sudo snap install --classic certbot
sudo ln -sf /snap/bin/certbot /usr/bin/certbot
sudo certbot --nginx -d estoque.<DOMINIO> -d portal.<DOMINIO>

Na primeira vez, o Certbot pede um e-mail (para avisos de expiração; use um e-mail que alguém acompanhe) e a aceitação dos termos. Ele altera os arquivos dos sites, adicionando o HTTPS e o redirecionamento automático de HTTP para HTTPS.

Validar

sudo nginx -t
sudo certbot certificates
sudo certbot renew --dry-run
systemctl list-timers | grep -i certbot

Resultados esperados: certificates lista os domínios com a data de validade (cerca de 90 dias); renew --dry-run termina com sucesso (a renovação vai funcionar); existe um timer do certbot agendado.

No navegador, abra https://estoque.<DOMINIO> e https://portal.<DOMINIO>: devem aparecer com o cadeado. Acessar pelo http:// deve redirecionar para https://.

Com o HTTPS funcionando por algumas semanas, você pode adicionar o cabeçalho Strict-Transport-Security nos blocos listen 443, para que os navegadores passem a usar sempre HTTPS. Não faça isso antes de ter certeza de que a renovação funciona.

23. Receita para adicionar uma nova aplicação

Executar em: vm-banco e vm-apps

Para cada aplicação nova, repita esta sequência. Exemplo: aplicação <app> na porta <porta>.

Na vm-banco (se usar banco)

  1. Gere a senha e crie usuário e banco (etapa 12): <app>_user e <app>_db.
  2. Acrescente a linha no pg_hba.conf (etapa 11.2) e aplique com sudo systemctl reload postgresql.
  3. O backup diário já inclui o banco novo automaticamente.

Na vm-apps

  1. Crie a deploy key, o apelido e clone o repositório como apps (etapa 17).
  2. Node.js: crie o .env com a próxima porta livre, rode npm ci --omit=dev, acrescente um bloco no ecosystem.config.cjs e execute como apps: pm2 start /srv/apps/ecosystem.config.cjs --only <app> e pm2 save (etapa 18).
  3. Crie o site no Nginx copiando o modelo: sudo cp /etc/nginx/sites-available/estoque /etc/nginx/sites-available/<app>. Troque nome, logs e porta (ou use o modelo do portal, se for estática). Mas atenção: o arquivo do estoque já foi alterado pelo Certbot; apague do arquivo copiado as linhas marcadas com # managed by Certbot e o bloco de redirecionamento que ele criou, deixando só o listen 80.
  4. Ative, teste e recarregue: ln -s, sudo nginx -t, sudo systemctl reload nginx.
  5. Crie o registro DNS (etapa 21.2) e emita o certificado: sudo certbot --nginx -d <app>.<DOMINIO>.
  6. Atualize a tabela de aplicações da etapa 2 e as Notes da VM no Proxmox.

24. Atualizar uma aplicação com um comando

Executar em: vm-apps

Depois do git push no seu computador, a atualização no servidor é sempre a mesma sequência. Um script evita esquecer algum passo:

sudo -iu apps
nano /srv/apps/bin/atualizar.sh
#!/usr/bin/env bash
# Uso: /srv/apps/bin/atualizar.sh <nome-da-aplicacao>
set -euo pipefail

APP="${1:?Informe o nome da aplicação. Exemplo: atualizar.sh estoque}"
DIR="/srv/apps/$APP"

[ -d "$DIR/.git" ] || { echo "Pasta $DIR não é um repositório Git"; exit 1; }
cd "$DIR"

echo "==> Versão atual:  $(git log --oneline -n 1)"
git pull --ff-only
echo "==> Versão nova:   $(git log --oneline -n 1)"

if [ -f package.json ] && pm2 describe "$APP" > /dev/null 2>&1; then
  echo "==> Instalando dependências"
  npm ci --omit=dev
  echo "==> Reiniciando $APP"
  pm2 reload "$APP"
  sleep 3
  pm2 status "$APP"
else
  echo "==> Aplicação estática: nada a reiniciar"
fi

echo "==> Atualização concluída"
chmod 750 /srv/apps/bin/atualizar.sh
/srv/apps/bin/atualizar.sh estoque
exit

Para usar direto da sua conta, sem entrar como apps: sudo -iu apps /srv/apps/bin/atualizar.sh estoque.

Se a atualização mudar a estrutura do banco (migrations), execute o passo de migração do README da aplicação antes do pm2 reload, e confirme antes que o backup da noite anterior existe. Se o git pull --ff-only falhar, alguém alterou arquivos direto no servidor: investigue com git status em vez de forçar.
