1. Como usar este guia e os conceitos básicos

Execute as etapas na ordem. Cada etapa explica o objetivo, apresenta os comandos e diz o que você deve ver como resultado. Marque a caixa da etapa somente depois de confirmar o resultado.

Os comandos são executados no PowerShell do seu computador, salvo quando a etapa indicar terminal do servidor Linux. Substitua todos os valores entre sinais de maior/menor, como <SEU_USUARIO>, antes de executar. Não cole os sinais de maior/menor literalmente.

Git e GitHub não são a mesma coisa

TermoO que é
GitPrograma instalado no seu computador que registra o histórico de alterações dos arquivos de uma pasta.
GitHubSite que guarda uma cópia desse histórico na nuvem. Funciona como backup, permite acessar o código de qualquer lugar e facilita levar o código ao servidor.
RepositórioUma pasta de projeto controlada pelo Git. Use um repositório por aplicação.
CommitUm "ponto de salvamento" com as alterações e uma mensagem explicando o que mudou. Você pode voltar a qualquer commit.
PushEnviar seus commits do computador para o GitHub.
PullTrazer para o computador (ou servidor) os commits que estão no GitHub.
BranchUma linha de trabalho paralela. A principal se chama main; outras servem para testar mudanças sem afetar a principal.

Fluxo que você vai montar:

Seu computador (Windows)
  │ git commit  → salva a alteração no histórico local
  │ git push    → envia para o GitHub
  ▼
GitHub (repositório privado)
  │ git pull    → servidor busca a versão nova (somente leitura)
  ▼
Servidor Ubuntu (VM de aplicações no Proxmox)
Regra para quem está começando: antes de qualquer git add ou git commit, rode git status e leia a saída. Esse comando nunca altera nada e mostra exatamente o que o Git vai fazer.

2. Criar a conta no GitHub e ativar a autenticação em dois fatores

  1. Acesse github.com/signup e crie a conta. Prefira o e-mail corporativo e um nome de usuário profissional (ele aparece nos endereços dos repositórios).
  2. Confirme o e-mail recebido.
  3. Ative a autenticação em dois fatores em Settings → Password and authentication → Two-factor authentication, usando um aplicativo autenticador no celular.
  4. Baixe os códigos de recuperação e guarde-os no cofre de senhas da empresa. Sem eles, perder o celular pode significar perder o acesso à conta.
Conta pessoal ou organização? Para começar, repositórios privados na sua conta resolvem. Se outras pessoas forem trabalhar no código, ou para que o código pertença à empresa e não a uma pessoa, crie depois uma Organization gratuita no GitHub e transfira os repositórios para ela.

3. Instalar o Git no Windows

Abra o PowerShell e instale o Git pelo gerenciador de pacotes do Windows:

winget install --id Git.Git -e --source winget

Se o winget não existir no seu Windows, baixe o instalador em git-scm.com/download/win e aceite as opções padrão.

Feche e abra o PowerShell de novo (o terminal só enxerga programas novos depois de reaberto) e confira:

git --version

Resultado esperado: algo como git version 2.x.x.windows.x. Se aparecer "git não é reconhecido", reinicie o computador e teste novamente.

Dica: o Visual Studio Code tem integração visual com o Git (painel de alterações, diferenças coloridas). Vale usar junto, mas aprenda primeiro pelos comandos deste guia: assim você entende o que os botões fazem.

4. Configurar sua identidade no Git

Todo commit registra quem o fez. Configure isso uma única vez no computador:

git config --global user.name "<Seu Nome Completo>"
git config --global user.email "<SEU_EMAIL>"
git config --global init.defaultBranch main
git config --global core.autocrlf true
git config --global --list
ConfiguraçãoPara que serve
user.name e user.emailIdentificam o autor dos commits. Use o mesmo e-mail cadastrado no GitHub para os commits aparecerem vinculados à sua conta.
init.defaultBranch mainFaz os repositórios novos começarem com a branch main, o mesmo nome padrão do GitHub.
core.autocrlf trueO Windows e o Linux marcam o fim de linha de formas diferentes. Essa opção converte automaticamente e evita arquivos "alterados" sem mudança real.
Privacidade do e-mail: se preferir não expor seu e-mail no histórico, o GitHub oferece um endereço do tipo numero+usuario@users.noreply.github.com em Settings → Emails. Use esse endereço em user.email.

5. Criar uma chave SSH e cadastrá-la no GitHub

A chave SSH permite que o computador envie código ao GitHub sem digitar senha e sem guardar senha em arquivo. Ela tem duas partes: a privada (fica só no seu computador, nunca é enviada) e a pública (pode ser cadastrada em serviços).

5.1 Gerar a chave

Se você já gerou uma chave id_ed25519 para acessar os servidores, pode reutilizá-la: pule para 5.2. Caso contrário, no PowerShell:

ssh-keygen -t ed25519 -C "<SEU_EMAIL>"

Aceite o local padrão com Enter e defina uma frase-senha (passphrase). Ela protege a chave caso alguém copie o arquivo.

5.2 Copiar a chave pública

Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard

A linha pública, que começa com ssh-ed25519, foi copiada para a área de transferência.

Nunca copie nem envie o arquivo id_ed25519 sem extensão. Ele é a chave privada. O único arquivo que vai para o GitHub é o .pub.

5.3 Cadastrar no GitHub

  1. No GitHub, clique na sua foto → Settings → SSH and GPG keys → New SSH key.
  2. Em Title, identifique o equipamento, por exemplo Notebook trabalho.
  3. Em Key type, mantenha Authentication Key, cole a chave em Key e salve.

5.4 Testar a conexão

ssh -T git@github.com

Na primeira vez, o SSH pergunta se você confia no servidor e mostra uma impressão digital (fingerprint). Compare com as impressões publicadas na documentação do GitHub (veja as referências) e responda yes. Resultado esperado:

Hi <SEU_USUARIO>! You've successfully authenticated, but GitHub does not provide shell access.

Essa mensagem significa sucesso: o GitHub reconheceu a chave. O aviso de que não há "shell access" é normal.

6. Preparar a pasta do projeto antes do primeiro commit

Esta é a etapa mais importante para a segurança. O Git guarda para sempre tudo o que entra em um commit. Senhas, chaves e arquivos gerados não podem entrar no repositório.

6.1 Criar o arquivo .gitignore

O .gitignore lista o que o Git deve ignorar. Na pasta raiz do projeto, crie um arquivo chamado exatamente .gitignore com o conteúdo:

# Dependências (são reinstaladas com npm ci)
node_modules/

# Segredos e configurações locais
.env
.env.*
!.env.example

# Logs
*.log
logs/
npm-debug.log*

# Arquivos enviados pelos usuários e dados locais
uploads/
storage/

# Arquivos do sistema operacional
Thumbs.db
.DS_Store

Para criar o arquivo pelo PowerShell com o Bloco de Notas:

cd <CAMINHO_DA_PASTA_DO_PROJETO>
notepad .gitignore
O Bloco de Notas pode salvar como .gitignore.txt. Confira com Get-ChildItem -Force: o nome deve ser exatamente .gitignore. Se estiver errado, corrija com Rename-Item .gitignore.txt .gitignore.

6.2 Criar o .env.example

Se a aplicação usa um arquivo .env com senha do banco e outras configurações, crie uma cópia chamada .env.example com os mesmos nomes de variáveis, mas sem os valores reais. Ele entra no repositório e documenta o que precisa ser configurado no servidor.

# .env.example — valores de exemplo, NUNCA reais
PORT=3000
DATABASE_URL=postgres://<usuario>:<senha>@<host>:5432/<banco>
SESSION_SECRET=<gerar-no-servidor>

6.3 Procurar senhas escritas direto no código

Procure senhas, tokens ou endereços de banco digitados no código-fonte:

Get-ChildItem -Recurse -File -Exclude *.png,*.jpg,*.pdf | Where-Object { $_.FullName -notmatch 'node_modules' } | Select-String -Pattern 'password|senha|secret|token|postgres://' | Select-Object Path, LineNumber, Line

Se encontrar valores reais no código, mova-os para o .env e leia-os com process.env.NOME_DA_VARIAVEL antes de continuar.

6.4 Criar um README.md

Crie um arquivo README.md explicando o que a aplicação faz, como instalar e quais variáveis precisa. No futuro, você (ou um colega) vai agradecer. Um modelo mínimo:

# Nome da aplicação

Para que serve e quem usa.

## Requisitos
- Node.js <versão>
- PostgreSQL

## Instalação
1. npm ci
2. Copiar .env.example para .env e preencher
3. npm start

7. Criar o repositório privado no GitHub

  1. No GitHub, clique no + no canto superior direito → New repository.
  2. Em Repository name, use um nome curto, em minúsculas e com hífens, por exemplo controle-estoque.
  3. Escreva uma descrição curta.
  4. Marque Private. Repositórios públicos ficam visíveis para qualquer pessoa na internet.
  5. Não marque as opções de adicionar README, .gitignore ou licença: você já criou esses arquivos localmente, e criar também no GitHub gera um conflito no primeiro envio.
  6. Clique em Create repository.

Na página seguinte, clique em SSH e copie o endereço, que tem o formato:

git@github.com:<SEU_USUARIO>/<NOME_DO_REPOSITORIO>.git
Confira duas vezes que o repositório está como Private. Isso aparece ao lado do nome, no topo da página do repositório.

8. Fazer o primeiro commit e enviar ao GitHub

No PowerShell, dentro da pasta do projeto:

cd <CAMINHO_DA_PASTA_DO_PROJETO>
git init
git status

O git init transforma a pasta em repositório (cria a pasta oculta .git). O git status lista os arquivos "untracked", ainda não controlados.

8.1 Conferir o que será incluído

git add .
git status

O git add . prepara todos os arquivos (exceto os ignorados) para o commit. Leia a lista com atenção. Não podem aparecer node_modules, .env ou arquivos de upload. Para confirmar que o .env está sendo ignorado:

git check-ignore -v .env

Resultado esperado: a linha do .gitignore que ignora o arquivo. Se não mostrar nada e o .env aparecer no git status, pare, corrija o .gitignore e execute git rm --cached .env antes de continuar.

8.2 Criar o commit e enviar

git commit -m "Versão inicial da aplicação"
git remote add origin git@github.com:<SEU_USUARIO>/<NOME_DO_REPOSITORIO>.git
git push -u origin main
ComandoO que faz
git commit -m "..."Cria o ponto de salvamento local com a mensagem informada.
git remote add origin ...Liga a pasta local ao repositório do GitHub. origin é o apelido padrão desse endereço.
git push -u origin mainEnvia a branch main. O -u memoriza o destino: nas próximas vezes basta git push.

Validação: atualize a página do repositório no navegador. Os arquivos devem aparecer e o README.md é exibido abaixo deles. Confirme visualmente que não há .env nem node_modules.

Repita as etapas 6, 7 e 8 para cada aplicação. Ao final, todo o código estará com cópia fora do seu computador.

9. O ciclo do dia a dia: alterar, salvar e enviar

Depois do primeiro envio, o trabalho segue sempre o mesmo ciclo. Pratique com uma alteração pequena, como uma linha no README.md:

git pull                # 1. traz alterações feitas em outro lugar (bom hábito)
# 2. edite os arquivos normalmente no editor
git status              # 3. quais arquivos mudaram?
git diff                # 4. quais linhas mudaram? (tecla q para sair)
git add .               # 5. prepara as alterações
git commit -m "Adiciona filtro por data na tela de pedidos"
git push                # 6. envia ao GitHub

Como escrever boas mensagens de commit

A mensagem é o que você vai ler meses depois para descobrir quando e por que algo mudou. Descreva o que a alteração faz, no presente, em uma frase.

Boas
Corrige cálculo de total com desconto
Adiciona exportação de pedidos em CSV
Aumenta limite de upload para 20 MB
Ruins
ajustes
teste
agora vai

Faça commits pequenos e frequentes, um para cada assunto. É mais fácil entender e desfazer uma mudança pequena do que um commit com o trabalho da semana inteira.

10. Consultar o histórico e desfazer alterações

10.1 Ver o histórico

git log --oneline -n 20

Cada linha mostra um código curto (o hash, como a1b2c3d) e a mensagem do commit. No GitHub, o mesmo histórico aparece em Commits, na página do repositório.

10.2 Qual comando usar para desfazer

SituaçãoComandoEfeito
Alterei um arquivo, ainda não fiz git add, e quero voltar ao último commitgit restore <arquivo>Descarta as alterações desse arquivo. Não tem volta.
Fiz git add de um arquivo por enganogit restore --staged <arquivo>Tira o arquivo da preparação, mantendo suas alterações.
Errei a mensagem do último commit e ainda não fiz pushgit commit --amend -m "Nova mensagem"Reescreve a mensagem do último commit.
Um commit já enviado causou problemagit revert <hash> e depois git pushCria um novo commit que desfaz aquele. O histórico fica preservado.
Evite enquanto está aprendendo: git reset --hard e git push --force. Eles apagam trabalho e reescrevem o histórico do GitHub. Quase sempre existe uma alternativa segura, como o git revert.

11. Trabalhar com branches e Pull Requests

Quando a mudança for maior ou arriscada, trabalhe em uma branch separada. A main continua sendo a versão estável, que é a que vai para o servidor.

11.1 Criar a branch e trabalhar nela

git switch main
git pull
git switch -c relatorio-mensal
# edite, depois:
git add .
git commit -m "Cria relatório mensal de vendas"
git push -u origin relatorio-mensal

11.2 Abrir e concluir o Pull Request

  1. No GitHub, aparece o botão Compare & pull request. Clique nele.
  2. Descreva o que mudou e como testou. Clique em Create pull request.
  3. Na aba Files changed, revise as diferenças linha a linha. É uma ótima hora para encontrar erros.
  4. Estando tudo certo, clique em Merge pull request e confirme. As alterações entram na main.
  5. Clique em Delete branch para apagar a branch no GitHub.

11.3 Voltar para a main no computador

git switch main
git pull
git branch -d relatorio-mensal
Trabalhando sozinho, o Pull Request parece burocracia, mas ele cria o hábito de revisar antes de publicar e deixa registrado no GitHub o motivo de cada mudança. Para ajustes pequenos, commitar direto na main é aceitável.

12. Resolver um conflito

Um conflito acontece quando a mesma linha foi alterada em dois lugares (por exemplo, editada no GitHub e no computador). O Git não escolhe sozinho e pede sua decisão. Quando ocorrer em um git pull ou merge, o arquivo fica assim:

<<<<<<< HEAD
const limite = 20;
=======
const limite = 50;
>>>>>>> origin/main
  1. Abra o arquivo, decida qual versão fica (ou combine as duas) e apague as linhas de marcação <<<<<<<, ======= e >>>>>>>.
  2. Salve, teste a aplicação e finalize:
git status
git add <arquivo>
git commit -m "Resolve conflito no limite de itens"
git push

Se ficar confuso e quiser voltar ao estado anterior ao merge, use git merge --abort. Nada é perdido.

13. Criar uma chave de implantação (deploy key) no servidor

Terminal do servidor Linux. O servidor precisa baixar o código, mas não deve usar a sua chave pessoal: se o servidor fosse comprometido, a sua conta inteira ficaria exposta. A solução é uma deploy key: uma chave que dá acesso somente de leitura a um único repositório.

Execute como o usuário que fará as atualizações da aplicação no servidor. O exemplo usa a aplicação controle-estoque; repita para cada aplicação trocando o nome.

13.1 Gerar a chave no servidor

git --version || sudo apt install -y git
mkdir -p ~/.ssh && chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/github_controle-estoque -N "" -C "deploy controle-estoque"
cat ~/.ssh/github_controle-estoque.pub

A opção -N "" cria a chave sem frase-senha, para que o servidor consiga usá-la sem ninguém digitar nada. Por isso ela deve ter permissão apenas de leitura.

13.2 Cadastrar no repositório

  1. No GitHub, abra o repositório → Settings → Deploy keys → Add deploy key.
  2. Em Title, use o nome do servidor, por exemplo vm-aplicacoes. Cole a linha exibida pelo cat.
  3. Não marque Allow write access. Salve.

13.3 Criar um apelido para a chave

O GitHub não permite usar a mesma deploy key em dois repositórios. Com várias aplicações no mesmo servidor, cada uma tem sua chave, e um apelido no arquivo de configuração do SSH indica qual chave usar:

nano ~/.ssh/config
Host github-controle-estoque
    HostName github.com
    User git
    IdentityFile ~/.ssh/github_controle-estoque
    IdentitiesOnly yes
chmod 600 ~/.ssh/config
ssh -T git@github-controle-estoque

Confira a impressão digital como na etapa 5.4 e responda yes. Resultado esperado: Hi <SEU_USUARIO>/controle-estoque! You've successfully authenticated... — o nome do repositório na mensagem confirma que é a deploy key.

14. Baixar a aplicação no servidor pela primeira vez

Terminal do servidor Linux. Clone usando o apelido criado, no lugar de github.com:

sudo mkdir -p /srv/apps
sudo chown $USER:$USER /srv/apps
cd /srv/apps
git clone git@github-controle-estoque:<SEU_USUARIO>/controle-estoque.git
cd controle-estoque
git log --oneline -n 3

O último commit exibido deve ser o mesmo que aparece no GitHub.

14.1 Criar o .env no servidor

O .env não veio com o código, e é assim que deve ser. Crie-o no servidor a partir do exemplo e preencha com os valores reais de produção:

cp .env.example .env
nano .env
chmod 600 .env

Depois instale as dependências e inicie a aplicação conforme a configuração do servidor (PM2 ou serviço systemd):

npm ci --omit=dev
O npm ci instala exatamente as versões registradas no package-lock.json. Por isso esse arquivo deve estar no repositório. Se ele não existir, rode npm install no seu computador, faça commit do package-lock.json gerado e envie.

15. Atualizar a aplicação no servidor

A partir de agora, publicar uma nova versão é: fazer git push no seu computador e, no servidor, buscar a versão nova.

cd /srv/apps/controle-estoque
git status                    # deve dizer "nothing to commit, working tree clean"
git pull --ff-only
npm ci --omit=dev
# reinicie a aplicação conforme a configuração do servidor, por exemplo:
pm2 restart controle-estoque  # ou: sudo systemctl restart controle-estoque
git log --oneline -n 1

O --ff-only garante que o servidor apenas avance para a versão do GitHub. Se alguém tiver editado arquivos direto no servidor, o comando para com erro em vez de misturar alterações, e você pode investigar com git status.

Nunca edite código direto no servidor. Toda alteração nasce no seu computador, passa por commit e push, e só então chega ao servidor com git pull. Assim o GitHub é sempre a fonte da verdade.

Voltar para a versão anterior se a atualização der problema

A forma segura é desfazer no computador com git revert <hash> (etapa 10), enviar e repetir o git pull no servidor. Se a aplicação alterou o banco de dados, avalie também a restauração do banco antes.

16. Se uma senha ou chave for enviada ao GitHub por engano

Mesmo em repositório privado, trate o segredo como vazado. Apagar o arquivo em um commit novo não resolve: o valor continua no histórico.

  1. Primeiro, troque o segredo: altere a senha do banco, gere um novo token ou nova chave. Essa é a única medida que realmente elimina o risco.
  2. Atualize o valor novo no .env do servidor e reinicie a aplicação.
  3. Pare de rastrear o arquivo e garanta que ele está no .gitignore:
git rm --cached .env
git commit -m "Remove .env do controle de versão"
git push
O GitHub tem proteção contra envio de segredos conhecidos (push protection e secret scanning) e pode bloquear o push ou alertar você. Se receber esse aviso, não contorne o bloqueio: remova o segredo do código e troque o valor.

Quando estiver em dúvida, estes comandos só consultam e nunca alteram nada:

git status
git remote -v
git log --oneline -n 10
git branch -a
